systemLinux is made by the people who use it. Everything happens on GitHub.

Reporting bugs

Open an issue with:

  • the systemLinux version (cat /etc/os-release) and how you installed (Handbook or quick install)
  • what you did, what you expected, and what happened
  • the exact error. For a failed port build: the port name and the first error in the output (rebuild with -k to keep the build directory)

Ports

Ports are the easiest place to start: test them, fix the ones that fail, add new ones. The Packaging guide explains recipes. Work from a clone of the repository and point get at it:

$ git clone https://github.com/tortr-rs/systemLinux
$ cd systemLinux
$ sudo GET_PORTS=$PWD/ports get install -k NAME
$ tools/ports-check.sh                     # checks every recipe

Then open a pull request.

The wiki

The wiki is website/wiki/ in the repository. Each page is an HTML file whose own content sits between <!-- content --> and <!-- /content -->; tools/website.py adds the header, navigation, table of contents and footer. To change a page:

  1. Edit the content of website/wiki/PAGE.html (the "Edit this page on GitHub" link opens it).
  2. Run tools/website.py to rebuild the pages.
  3. Open a pull request. The website is published when it is merged.

A new page also needs a line in the WIKI list at the top of tools/website.py (file name, title, category). Conventions:

  • Write what systemLinux does, not what it should do. Say so when something is missing or untested.
  • Every command must work as written, on the current release.
  • <h2> and <h3> headings make the table of contents. A line <!-- related: page page --> makes the "Related articles" box.
  • Commands go in <pre class="term"> with the prompt in <span class="p"> ($ user, # root, (chroot) # in a chroot) and comments in <span class="c">.
  • Boxes: <div class="note">, <div class="tip">, <div class="warning">, each starting with <strong>Note:</strong> and so on.

The system itself

The base system, the installer, the initramfs and the ISO build are in the repository too; see Building the ISO. Larger changes are best discussed in an issue first.
